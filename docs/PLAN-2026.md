# Tengen 2026 Plan — the build roadmap

This is the plan the team wrote (Noah's notes + the #coding discussion), turned into a buildable
roadmap. For each item: **what it means**, **how it lands on what we already have**
(see [HOW-TENGEN-WORKS.md](HOW-TENGEN-WORKS.md)), rough **effort**, and what it **depends on**.
Open decisions are flagged **⚠ DECIDE** — those need a human call before code.

> **The goal, in one line:** minimize conflicts with our alliance, maximize our scores, and use
> data to choose autos, strategy, and alliance picks. Keep Tengen private until it's good; share
> tools, not our auto-building methods.

---

## Priorities (the agreed "do first" order)

1. Fix tracking when robots are occluded.
2. Decide storage (position data vs. video vs. local server), then implement it.
3. Library: scanned-match browsing, timestamp sorting, path overlays.
4. AdvantageScope integration.
5. Auto + teleop heatmaps and the effective-zone map.
6. Alliance-pick engine.
7. Windows app packaging + security hardening.

The rest of this doc is each of those in depth, plus the strategy engine and the open questions.

---

## 1. Robot tracking through occlusion  ·  effort: M–L  ·  the #1 ask

**What:** stop losing which robot/team is which when a robot goes behind another or off-panel.
**Where it lands:** Stage 2 of the engine (`training/track_yolo.py`). The size-gate and
stale-recovery fixes are already in and roughly doubled "all six tracked" on the Champs test.
**The real lever is data, not just code:** the detector barely sees 2026 footage yet
(held-out recall ~64%). Plan:
- Label more 2026 frames, concentrating on **occlusion moments and re-entries** (that's where
  identity breaks), via the labeler (`robot_box_labeler.py`, `docs/LABELLING.md`).
- Retrain, score on the held-out pack, record in the registry. Target: "all six tracked" >85% of
  a match, >90% detection recall. Loop in `docs/IMPROVING-THE-MODEL.md`.
- Consider appearance/colour ReID cues for same-alliance swaps (two red robots trading IDs is the
  stubborn case).
**Depends on:** labelling throughput. This is the gating item for everything strategy-shaped.

## 2. Simulation / prediction testbed  ·  effort: L  ·  ✓ DECIDED: full physics field sim (b)

**What:** sim software so robot predictions can be tested ("if we think team X runs auto Y,
replay it and check").
**Where it lands:** new, but feeds on existing tracks/field-coordinate output. Two flavours were
on the table: **(a)** a lightweight replay/overlay that plays predicted paths against actual ones
(cheap, high value, pairs with path overlays in §3), or **(b)** a physics-ish field sim (big).
**Decision (2026-10-30):** go with **(b)**, the full physics field sim. This is the larger build,
so it sequences *after* §1 (tracking/data must be trustworthy before a sim is worth believing) and
after §3's path overlays, which give the sim its replay substrate. The lightweight replay from (a)
is still worth building first as a stepping stone to validate the sim against real paths.

## 3. Match library + timestamps + path overlays  ·  effort: M

**What:** a browsable library of scanned matches; sort/scrub by timestamp; overlay multiple
robots' paths on one field view. First official event only.
**Where it lands:** data's already there (tracks per job, thinned to 10 Hz). This is mostly
**web/desktop UI** (`web/src/views/`, `desktop/`) plus a library index endpoint on the API
(`ingest/main.py`). Path overlay = draw N tracks on the one top-down field we already compute.
**Nice follow-on from the chat (Savage/pistol):** link the video to a **live heatmap** with
**clickable points** — click a hot spot, jump the video there. Very doable once overlays exist.
**Depends on:** storage decision (§Storage) for how the library pulls match data.

## 4. AdvantageScope integration  ·  effort: M–L  ·  ✓ DECIDED: integrate with AdvantageScope

**What:** feed Tengen's position/driving data into AdvantageScope; longer term, the
"AI-controlled robot like that team" idea.
**Where it lands:** new export adapter. AdvantageScope ingests structured log data; our tracks
are already structured field-coordinate timeseries, so this is largely a **format bridge**.
**Decision (2026-10-30):** **integrate** with AdvantageScope (fast, standard, what drivers know)
rather than build a custom viewer. A custom viewer is a fallback only if AdvantageScope can't show
what we need. The AI-robot-control idea is a research track, not a season deliverable — park it.
**Status:** export **shipped** (`ingest/strategy/advantagescope.py`): `python -m ingest.strategy
advantagescope <run>` writes a `.wpilog` per match — one 2D pose entry per robot
(`/Tengen/<alliance>/<team>`, `[x_m, y_m, heading_rad]`) that AdvantageScope's 2D Field reads as a
Pose2d. Field coords are converted feet→metres; heading comes from the direction of travel (no gyro).
Next: a one-click export from the desktop app, and 3D/mechanism data once we measure more than pose.

## 5. Heatmaps + effective zones  ·  effort: M  ·  the strategic core

**What:**
- **Auto heatmaps** — where each of the six robots is likely to go in autonomous.
- **Teleop heatmaps** — where enemy robots are strongest and shoot from.
- **Effective / non-effective zones** — mark where a team *succeeds* (scores), to define the zones
  worth contesting.
- **Our own robot too** — so drivers see where *we're* most effective.
**Where it lands:** the strategy layer already computes shooting spots, dwell, and zones per team
(`ingest/strategy/features.py`, `profile.py`); heatmaps are the **visual aggregation** of that
over matches, rendered on the top-down field. The web already has a `HeatMap` view to build on.
**Data honesty rule (from the chat):** practice-match data is noisy — teams test systems, so
don't trust behaviour, **only trust scoring locations**. Encode that: weight/flag practice data,
and build effective zones from *scores*, not from movement.
**Status:** scoring heatmap + effective zones **shipped** (`ingest/strategy/heatmap.py` `scoring_map`,
practice scoring kept, recency-weighted), and the **auto heatmap shipped** (`auto_map`, official
matches only — practice auto is excluded as noise), both rendered on the web Team Profiles view and
any team including our own. Still open from this section: a **teleop dwell/movement** heatmap (needs
teleop position samples lifted into the feature pipeline, not just the scoring points we have now).

## 6. Strategy engine — autos, teleop, defense  ·  effort: L

**What:** turn heatmaps into recommendations.
- **Auto:** from the six auto-heatmaps, recommend the auto with **least conflict with our
  alliance, most with the opponent**; also a defense-maximizing auto with AI path choice. Lean on
  the fact that 50–75% of teams run only 2–3 autos — they're predictable.
- **Teleop:** find patterns in where enemies score and **go there**; preventing their scoring is
  the highest-value play; give drivers "where you're most effective" maps.
- **Team lookup:** look up any team's autos, matches, and history.
**Where it lands:** new recommendation layer on top of profiles. This is the payoff of §1–5 —
sequence it after the data it needs is trustworthy.
**Status:** first cut **shipped** (`ingest/strategy/engine.py`, `build_matchplan`): `python -m
ingest.strategy matchplan <runs> --us 254,1678,971 --them 148,118,2056` prints an alliance plan
with the evidence behind each call — auto partner-conflict splits (teams sharing a hot auto cell),
predictable opponent autos to contest, teleop deny zones (opponents' pooled effective zones), our
own strength zones to feed, and defenders to expect. Still open: a defense-maximizing *AI path*
choice, and surfacing the plan in the web/desktop UI (it is CLI-only for now). Accuracy rides on
§1 — the calls are only as good as the profiles under them.

## 7. Alliance-selection engine  ·  effort: L  ·  must be FAST and live

**What:** ignore official rankings; build our own top-18. Given our seed, simulate the pick order,
auto-suggest our best available pick, and evaluate the four 2-robot combinations to answer "which
unpicked robot makes us better than any of those?" Output: our two best partners, favouring most
offensive power and fewest conflicts. Help decide whether to **accept** a pick, and run
roleplay scenarios ("1 picks 2, 3 picks 4"). **Updates live as data comes in.**
**Where it lands:** new engine over team profiles + a conflict model (conflicts = two robots
wanting the same zone/lane/time — we already measure zones and lanes, so conflict is derivable).
**Hard requirement:** sub-second recompute during a live draft. Design it to run on cached
profiles, not re-analysis.
**Status:** first cut **shipped** (`ingest/strategy/picklist.py`): `python -m ingest.strategy
picklist <runs> --us 254 [--available ...]` ranks our own pick list by offensive power (shots/match)
minus conflict with us, reusing the match engine's conflict model (shared auto cells + shared
scoring zones). Also `best_pick`, `alliance_strength` for roleplay ("1 picks 2, 3 picks 4"), and
`should_accept` for accept-vs-decline. It is pure arithmetic over cached profiles, so it meets the
sub-second/live bar. Still open: wiring it live into a draft UI, and it inherits §1's data-quality
dependence — the ranking is only as trustworthy as the profiles. Power is shots/match for now; a
richer power model (reliability, endgame, defense value) is the obvious next refinement.

## Storage — the decision to make now  ·  ✓ DECIDED: data-first + local HDD + demo clips (A+C+B)

The confusion in the chat, resolved: **position data is already the primary store and it's tiny.**
The only heavy thing is the **480p video copies** (the ~100-match Supabase ceiling). So the real
choice is about *video*, not data:

| Option | What it means | Trade-off |
|---|---|---|
| **A. Position-data-first (default)** | Store tracks everywhere; the client **reconstructs** the match from positions. Video becomes optional. | Cheapest, syncs to everyone, GRFD's proposal. Loses "watch the real clip" unless paired with a link. |
| **B. Keep cloud video** | Current 480p-to-Supabase. | Simple, but the ~100-match wall and ongoing storage tax. |
| **C. Local server / 1TB HDD library** | Big library lives on team hardware; cloud holds data only. | Lots of room; if it goes down, Tengen still works, just no library (Savage's point). |

**Decision (2026-10-30): A + C + B.** **A as the foundation** (it's basically already true), **C
for the full video library** (team HDD/local server), and keep **B** only for the public web demo's
handful of showcase clips. That gives: everyone syncs lightweight data, the big library is cheap and
team-owned, and the public site still has something to show. This directly serves "scans upload to
the cloud and sync to everyone's PC" — it's the *data* that syncs, video stays local/optional.

**Video source:** YouTube links are supported, but keep them a convenience, not the backbone —
YouTube is blocked in some regions and cloud servers can't stream it anyway (that's *why* we make
the 480p copy). Position data + optional local video doesn't depend on YouTube at all.

## Platform + hardening

- **Windows app** — package the desktop app as a proper Windows application for convenience
  (confirmed yes). `desktop/` + a packaging step; there's already `Launch Tengen.cmd`.
- **Security** — build on what's there (header keys, read/write split, signed expiring video
  links, secrets out of the repo — see HOW-TENGEN-WORKS §5). Add: a real secrets rotation habit,
  rate limiting on the API, dependency updates, and a short threat-model note before the site is
  public. pistol's "24 hours" worry is answered by *not* exposing anything that isn't already
  behind a key.
- **Privacy / IP** — keep Tengen private until it works well. When we share, share the **tools**,
  not the auto-building methods and strategy engine. Practically: a public tier (viewer, demo
  clips) vs. a team-only tier (profiles, counters, pick engine) — the key system already supports
  exactly this split.
- **Link the website in Discord** — the info channel got purged; re-post the app + GitHub links in
  a pinned, read-only channel so they don't vanish again.

## Open questions — need a human decision

- **⚠ Train now, or wait for the season?** pistol: wait — robots may be built completely
  differently. GRFD: keep training detection now. **Reconcile:** *detection of robots-as-objects*
  generalizes and is worth training now; *strategy/behaviour* models should wait for real 2026
  robots. So: train detection/occlusion now, hold behaviour modelling. (This is a real
  disagreement — confirm the split.)
- **⚠ Storage model** — pick from the table above. Recommendation: A + C + B-for-demo.
- **⚠ AdvantageScope: integrate vs. custom** — recommendation: integrate first.
- **Meta Quest idea** — view what the other five robots are doing in VR/AR. Cool, parked as
  research; the field-coordinate data would feed it, but it's not a season deliverable.
- **Noah's caution** — over a competition, robots and the field "get smarter"; what a team starts
  with isn't what they end with. **Encode this:** weight recent matches more heavily, and never
  lock early-qualifier assumptions into the pick engine. Good instinct — make it a model property,
  not a footnote.

## Suggested sequencing

```
Now        │ Occlusion/identity (data + model)   ← gates everything strategic
           │ Storage decision + implement         ← gates library & sync
Next       │ Library + timestamps + path overlays
           │ Heatmaps + effective zones
Then       │ Strategy engine (auto/teleop/defense)
           │ Alliance-pick engine (live, fast)
Alongside  │ AdvantageScope bridge · Windows packaging · security hardening
Research   │ Sim (physics), AI robot control, Meta Quest
```

Everything strategic sits on two foundations: **trustworthy tracking** and **a settled storage
model**. Land those two and the rest is build-out on data we already produce.
